## 5. 本批关键结论（长期）

1. **自动化必须与目标进程同坐标系**：Windows 的 125% 缩放会让 DPI 不感知进程看到「虚拟桌面」（1792×1120），而 PerMonitorV2 应用用物理像素（2240×1400）。凡是用枚举矩形算点击点的脚本，先 `SetProcessDpiAwareness(2)`，否则一律偏移。**且不要用 `Visual.PointToScreen` 定位**：本机实测它对 Dock 窗口返回的原点与 `GetWindowRect` 相差 (164, 247)，命中判定走的是 HWND 真实矩形——用 `GetWindowRect + TransformToAncestor` 才与真实点击对齐。
2. **心跳间隔不能贴着急救阈值**：阈值/2 只剩 1 次丢帧余量，交互期一次 5s 级调度延迟就触发假阳性；阈值/3（3 帧/窗口）才稳。代价是 +3 次 UI 唤醒/30s ≈ +0.15% CPU，已计入 8.1 复核表。
3. **假阳性比漏判更伤**：误判会写出恢复事件，下次启动弹「上次异常退出」，属于用户可见的错误信息。因此超时判定必须打印「已收帧数 / 距最后一帧 / 宿主是否存活」，把假阳性和真卡死分开。
4. **自包含单文件可行**：运行时包必须联网 restore，但只影响**发布**这一步——`src/NuGet.config` 保持清空包源（日常构建仍完全离线），发布时用 `-p:RestoreSources` 单点注入即可，两者不冲突。
5. **长稳实证要用可续采的采样器**：一次性 `--sample-seconds 86400` 中途被打断就全废；`stability_m1.py` 逐行 flush + `--summary` 汇总，崩溃即停并保留证据（不自动重启掩盖问题）。
6. **「内存」必须说清口径（新）**：工作集会被 OS 主动 trim（同一进程在 8 分钟内从 199MB 掉到 32MB 再涨回 58MB），**它既不能横向比较也不能判泄漏**；私有字节（commit charge）才是真实占用，本机稳定 136~140MB。同步观察 GDI/USER 对象只有 24/40，句柄从 637 涨到 674 属内核句柄（图标/DWM/文件），不是经典 GDI 泄漏，需长跑继续观察是否收敛。
7. **「关闭瞬间涨了」不等于泄漏（新）**：预览面板关闭瞬间 GDI 常 +2，但下一轮起点又回到原值（26↔28 振荡）。判定泄漏必须看**跨轮绝对值漂移**；按「单轮增量 > 0」判会把抖动误报成泄漏（本工具的判定逻辑为此改过一次）。6 轮实测 GDI 漂移 +2、私有字节漂移 -1MB → 首轮那 1.4s CPU / +30MB 是 JIT + 首次 DWM 注册的一次性成本（K-20）。
8. **预热必须与漂移分离（新，最重要）**：冷启动后每**首次**走通一种交互路径都会抬升一截内存（本机 129.7 → 216.3MB / 42 分钟），而同类交互走顺后净增长为 0。所以「24h 内存增长 ≤5MB」这类指标，**基线必须取在预热之后**——否则测到的是预热曲线，不是泄漏。`stability_m1.py` 已把预热做成默认步骤，并用 `suspected_interaction` 把期间被用户打断的样本单列，避免「一次鼠标划过 = +20MB」带偏整份结论。
9. **不要用「单点跳变幅度」判泄漏（延伸 K-20）**：D 段（短驻留）每轮 +8.67MB 看着最像泄漏，但增量逐轮衰减到 +1.3MB；真正区分「预热」和「泄漏」的是**同一条路径重复 N 轮后的净增长是否收敛**。同理，B 段（进面板停留）比 C 段（点击激活）涨得多，是因为它把面板留在屏幕上更久，而不是因为它更「漏」。
