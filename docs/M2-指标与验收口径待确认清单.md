## C-1 空闲 CPU：判定窗口必须先定（对应 K-13）

| 项 | 内容 |
| --- | --- |
| 需求原文 | §8.1「空闲 CPU（无鼠标交互）≤ **0.3%**，测量方法：**任务管理器 5 分钟平均**」；AC-20 同 |
| 同一份代码的两种结果 | 5 分钟滚动平均 **0.172~0.187%（达标率 1.0）**；30 秒单次平均 **0.573%（超标）** |
| 差异根因 | Windows CPU 记账粒度 **15.6ms**：UI 线程每次唤醒无论干多少活都记满一格。看门狗心跳 3.3s/次 → 30s 窗口里 9 次唤醒 ≈ 0.14s/30s ≈ 0.47%；放到 5 分钟窗口被摊薄到 ≈ 0.05% |
| 建议判定口径 | ① **只认 5 分钟窗口**（与原文一致），30s 短窗仅用于定位突发、不作验收；② 前提写明「光标不在 Dock 上、无面板打开」；③ 采样周期固定 60s、取滚动均值 |
| 若产品认为 5 分钟太长 | 备选：`behavior.watchdogEnabled=false` 时 0.104%，可作为「极简模式」对外承诺，但会牺牲 AC-11 的 10s 自愈 |
| 需要谁定 | 产品（口径）＋ 测试（写进验收脚本） |

## C-2 内存 ≤120MB 工作集（对应 K-01 / K-14）

| 项 | 内容 |
| --- | --- |
| 需求原文 | §8.1「内存（常驻，无缩略图面板）≤ **120MB 工作集**，测量方法：任务管理器」；AC-20 同 |
| 实测 | **冷启动**：工作集 199~201MB、私有字节 130~133MB；**预热后**（走过一次预览/点击激活）：私有字节抬升到 **~192MB 并常驻不回落**（K-21，静置 170s 仅 -2MB）；面板打开 6 缩略图另计（历史 234~240MB）。**判定前必须先说清取哪一档**，否则同一份代码能测出差 60MB 的结论 |
| 为什么单一数字不可判 | ① 工作集会被 OS 主动 trim（199MB→32MB→58MB）；② 私有字节随「是否用过预览/拖拽」分档（134MB vs 192MB）；③ 面板打开时又是第三档。**建议统一「预热后 + 无面板」作为常驻口径** |
| 结构性原因 | WPF 硬件渲染会映射 Intel 显卡用户态驱动（约 162MB 模块）；D3D 表面 + 渲染目标常驻。**软件渲染可压到 ~120MB，但帧率会从 ≥55FPS 掉下来**，与 AC-21 直接冲突 |
| 另一个坑：工作集不是稳定量 | OS 会主动 trim：同一进程 8 分钟内出现 199MB → **32MB** → 58MB 的跳变。所以「单点抓一个数」既可能超标也可能「达标」，**不可判** |
| 建议判定口径（三选一） | ① **改阈值**：按 WPF 技术栈把上限调到 220MB（工作集，5 分钟平均）；② **改口径**：判「私有字节 ≤150MB」＋「24h 增长 ≤5MB」（后者本来就是 8.2 的稳定性要求，更防泄漏）；③ **保留 120MB 但登记豁免**：M2 明确标注「未达标，结构性原因已量化」，M3 再评估原生渲染/DirectComposition 方案 |
| 我方建议 | ② 优先：真正影响用户的是 commit 占用与增长趋势，不是可被 trim 的工作集；同时保留 200MB 工作集的如实登记 |
| 需要谁定 | 产品（阈值/口径）＋ 架构（是否接受 M3 换渲染栈） |

## C-4 AC-21 帧率 ≥55FPS 缺测量手段（✅ 已落地，2026-11-10 第八批）

> 更新：`FrameRateCounter` + `--fps-probe` 已落地。60s 悬停实测**活跃突发平均 57.18 FPS ≥55 达标**。判定口径注意：**时间平均会被两段动画之间的空闲期稀释**（实测 4.9 FPS），判定必须用活跃突发口径；P5≈32 / ~9% 帧超 25ms 的偶发掉帧已如实登记（与 K-11 同源）。原缺口描述保留如下。

| 项 | 内容 |
| --- | --- |
| 需求原文 | §8.1「动画帧率 ≥55 FPS（60Hz），测量方法：内置帧率统计 / PresentMon」；AC-21「连续悬停 60s 平均帧率 ≥55」 |
| 现状 | 打点框架已有 `ui.animation_frame` 计数（每帧 +1，见 `MetricsService` 汇总行），**但没有换算成 FPS，也没有悬停期间的窗口统计** |
| 建议 | 内置统计加「1s 窗口 FPS + 悬停期间 P5/均值」即可自证（约 1 个工作日），并与 PresentMon 交叉验证一次；验收以工具输出为准 |
| 需要谁定 | 测试（确认证据形式），无需产品改需求 |

## C-5 AC-12 多缩放档位缺环境（部分进展：125% 脚本审计全过）

> 更新：`--dpi-audit` 已落地，125% 下五项检查全过；另发现 manifest 声明 PMv2 但 Windows 实际解析为 **per-monitor v1**（legacy `true/pm` 与 `PerMonitorV2` 并存所致）——坐标一致性不受影响，非客户区自动缩放差异对本应用影响有限，已登记观察。150%/200% 仍需真改系统缩放。原缺口描述保留如下。

| 项 | 内容 |
| --- | --- |
| 需求原文 | §8.3「DPI：100% / 125% / 150% / 175% / 200%，混合 DPI 多屏」；AC-12「100%/150%/200% 下 Dock 均清晰、无错位」 |
| 现状 | 本机**只有 125%**（2240×1400 物理 / 1792×1120 虚拟，已验证 PerMonitorV2 下坐标系一致）；150%/200% 无环境 |
| 已有教训 | 125% 下已踩到「虚拟 vs 物理像素混用」（K-19），说明该风险真实存在，不能用「布局是 DPI 无关的」一句带过 |
| 选项 | ① 提供可改缩放的测试机/虚机（最优）；② 接受「125% 实测 + 其余档位按下述静态核查」：`GetDpiForWindow` 动态取值、无硬编码像素常量、`TransformToAncestor` 换算（需评审认可）|
| 需要谁定 | 测试负责人（环境）＋ 评审（是否接受静态核查替代实测）|

## C-6 AC-11 心跳与 8.1 的张力（确认即可）

| 项 | 内容 |
| --- | --- |
| 需求原文 | §8.2 / AC-11「守护进程检测主进程 **10s** 未心跳 → 恢复原生任务栏」；§8.1 空闲 CPU ≤0.3% |
| 关系 | 10s 超时要留丢帧余量，心跳必须 ≤3.3s（阈值/3，K-18 假阳性修复后）→ UI 线程每 3.3s 必有一次唤醒 → 短窗口 CPU 必然上升 |
| 实测 | 5 分钟口径 **0.17~0.19% ≤0.3%**；关闭看门狗 0.104% |
| 结论 | 二者**可以同时满足**，前提是 CPU 按 5 分钟口径判（C-1）。不需要改需求，只需在验收记录里写明「看门狗默认开启状态下测得」|
| 需要谁定 | 评审（确认这条不构成验收异议）|
